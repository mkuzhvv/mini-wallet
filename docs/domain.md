# Доменная модель mini-wallet

## Что мы строим

платежная платформа с внутренними кошельками.

Сценарии:
- создание кошелька
- пополнение кошелька
- перевод между кошельками
- просмотр баланса
- просмотр выписки(история операций с кошельком)

Ограничения:
- одна валюта (RUB)
- без авторизации (userId передается клиентом) //возможно добавлю позже
- без отрицательного баланса
- без мультивалютности и конвертации(одна ваоюта RUB)

## Архитектура: CQRS
Система разделена на write model и read model.

- **Write model** — `ledger-service`. Хранит деньги и гарантирует корректность (ACID)
- **Read model** — `statement-service`. Хранит выписку, оптимизированную для чтения
- **payment-service** — принимает намерения клиента (платежные поручения) и передает команды в ledger

Потоки данных:

```text
Команда (синхронно, REST):
  payment-service -> ledger-service

События (асинхронно, Kafka):
  ledger-service -> Kafka -> statement-service
```

### Почему команды синхронные, а события асинхронные

Команда «выполни операцию» идет по REST синхронно: payment сразу узнает результат
(успех или бизнес-отказ) и может вернуть его клиенту

События «операция выполнена» идут через Kafka: их потребляют те, кому они нужны
(statement-service для построения read model, позже notification-service)
Это дает слабую связанность: ledger не знает, кто и зачем читает его события

Альтернатива (полностью асинхронные команды через Kafka) сложнее: нужна saga,
клиент должен поллинговать статус. Осознанно откладываем ее.

## Владение данными

| Сервис            | Сущности                                  |
|-------------------|-------------------------------------------|
| ledger-service    | Wallet, LedgerTransaction, LedgerEntry    |
| payment-service   | Payment                                   |
| statement-service | StatementEntry (read model)               |

Правило: сервис не ходит в чужие таблицы. Только REST и события.

## Сущности

### Wallet (ledger-service)

Кошелек пользователя.

- `id` (UUID) — идентификатор;
- `user_id` — владелец;
- `currency` — валюта (RUB);
- `status` — ACTIVE / BLOCKED;
- `balance` — доступный баланс (NUMERIC(19,2));
- `created_at`.

Инварианты:
- баланс пользовательского кошелька не может стать отрицательным
  (баланс SYSTEM уходит в минус — это выпущенные в систему деньги)
- баланс изменяется ТОЛЬКО вместе с проводками, в одной транзакции
- заблокированный кошелек не участвует в операциях

### Системный кошелек SYSTEM

Технический кошелек, источник денег для пополнений(например как банкомат - для поплнения кошелька пользователя извне)
Создается миграцией, не доступен через публичное API

Зачем нужен: чтобы каждая операция имела ровно две проводки
(списание откуда-то и зачисление куда-то) — это двойная запись.
Пополнение = перевод с SYSTEM на кошелек пользователя.

### LedgerTransaction (ledger-service)

Одна финансовая операция.

- `id` (UUID);
- `type` — DEPOSIT / TRANSFER;
- `status` — POSTED / REJECTED;
- `amount`, `currency`;
- `source_wallet_id` — для DEPOSIT это SYSTEM;
- `target_wallet_id`;
- `external_ref` — ссылка на Payment;
- `idempotency_key` (unique) — защита от двойного проведения;
- `created_at`.

Инварианты:
- операция атомарна: либо проведена целиком (POSTED) с двумя проводками, либо отклонена
- повторная команда с тем же `idempotency_key` не проводит деньги повторно
  а возвращает результат уже существующей операции

### LedgerEntry (ledger-service)

Проводка — одна сторона операции
         — это не намерение клиента. Намерение — это Payment/LedgerTransaction
         — это одна сторона движения денег: как операция повлияла на конкретный кошелек

- `id` (UUID);
- `transaction_id` — ссылка на LedgerTransaction;
- `wallet_id`;
- `direction` — DEBIT (списание с кошелька) / CREDIT (зачисление на кошелек);
- `amount` — положительная сумма;
- `created_at`.

Инварианты:
- проводки неизменяемы: их нельзя обновлять или удалять
- у операции ровно две проводки на одинаковую сумму, одна DEBIT, другая CREDIT

### Payment (payment-service)

Платежное поручение — намерение клиента, а не сами деньги.

- `id` (UUID);
- `idempotency_key` (unique) — приходит от клиента;
- `type` — DEPOSIT / TRANSFER;
- `source_wallet_id` (для DEPOSIT пустой);
- `target_wallet_id`;
- `amount`, `currency`;
- `status` — NEW / PROCESSING / SUCCESS / REJECTED / FAILED;
- `failure_reason` — код причины отказа;
- `created_at`, `updated_at`.

### StatementEntry (statement-service)

Готовая строка выписки, взглядом владельца кошелька. Read model

- `id` (UUID);
- `wallet_id`;
- `transaction_id`;
- `direction` — IN / OUT;
- `amount` — со знаком: «+» приход, «−» расход;
- `counterparty_wallet_id`;
- `description`;
- `occurred_at`.

Строится консьюмером из событий Kafka. Напрямую никем не пишется

## Статусы и переходы

### Wallet
- ACTIVE -> BLOCKED (блокировка)
- BLOCKED -> ACTIVE (разблокировка)

### LedgerTransaction
- создается сразу в POSTED или REJECTED (без промежуточных состояний, операция атомарна)

### Payment
- NEW -> PROCESSING (отправили команду в ledger)
- PROCESSING -> SUCCESS (ledger провел операцию)
- PROCESSING -> REJECTED (бизнес-отказ: недостаточно средств, кошелек заблокирован)
- PROCESSING -> FAILED (техническая ошибка: ledger недоступен, таймаут)
- FAILED -> PROCESSING (повторная попытка с тем же idempotency key)

### StatementEntry
- статусов нет, строка неизменяема после создания

## Ключевые решения (почему так)

### 1. Зачем idempotency_key у LedgerTransaction

Команда из payment может быть повторена (таймаут, retry). Без защиты ledger провел бы
деньги дважды. С unique `idempotency_key` повторная команда просто возвращает
результат существующей операции. Деньги проводятся ровно один раз.
- Идемпотентность нужна на каждом сетевом переходе. Ключ в Payment защищает
  повторы от клиента. Ключ в LedgerTransaction защищает повторы команды
  от payment (например, после таймаута, когда ledger выполнил операцию,
  а ответ потерялся). Обычно ключ для ledger равен id платежа

### 2. Зачем balance полем, если есть проводки

Читать баланс из поля — O(1). Считать из проводок — агрегация по истории, медленно.
Риск: поле может разойтись с проводками (баг, сбой).
Защита:
- баланс обновляется только в одной транзакции с проводками;

### 3. Почему проводки неизменяемы

Проводки — это аудит-лог денег. Если их можно править, историю можно подделать
и ошибки становятся ненаходимыми. Ошибочная операция исправляется НОВОЙ
операцией (reversal), а не правкой старой

### 4. REJECTED против FAILED

- REJECTED — бизнес-отказ (недостаточно средств). Повтор с теми же данными
  бессмыслен: результат не изменится. Идемпотентность возвращает тот же отказ.
- FAILED — технический сбой (сеть, недоступность). Повтор осмыслен:
  ledger мог выполнить команду, а ответ потерялся; retry с тем же
  idempotency key безопасен благодаря пункту 1.
