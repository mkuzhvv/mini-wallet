# Бизнес-правила mini-wallet

Правила описывают текущую реализацию. HTTP-коды ledger относятся к внутренней команде; публичный payment API возвращает результат в статусе платежа. Границы реализации перечислены в [PROJECT.md](PROJECT.md#границы-реализации).

## Общие

- R-01. Модель рассчитана на RUB. Создание кошелька с другой валютой возвращает 400; отдельной проверки совпадения валют операции и кошельков нет.
- R-02. Сумма должна быть положительной. Ограничения API на максимум и количество дробных знаков не заданы.
- R-03. Денежные значения представлены `BigDecimal` в Java и `NUMERIC(19,2)` в PostgreSQL.
- R-04. Владелец ресурса определяется из проверенного JWT, а не из поля запроса.

## Кошельки

- W-01. Кошелёк создаётся ACTIVE с нулевым балансом.
- W-02. Баланс обычного кошелька неотрицателен; защита есть в коде и CHECK-ограничении БД.
- W-03. BLOCKED-кошелёк не участвует в операции. Ledger возвращает 422 / WALLET_BLOCKED.
- W-04. SYSTEM служит источником DEPOSIT и может уходить в минус. Источником TRANSFER должен быть обычный кошелёк.
- W-05. У одного пользователя может быть несколько кошельков.
- W-06. Пользователь видит собственные кошельки; чужой UUID возвращает 404.

## Денежные операции ledger

- L-01. Операция атомарно сохраняет две проводки одинаковой суммы: DEBIT источника и CREDIT получателя.
- L-02. Источник и получатель должны различаться, иначе 400 / VALIDATION_ERROR.
- L-03. Для TRANSFER требуется достаточный баланс источника, иначе 422 / INSUFFICIENT_FUNDS.
- L-04. Повтор по `idempotency_key` возвращает существующую операцию после проверки владельца. Тело повторной команды отдельно не сравнивается.
- L-05. Проводки создаются вместе с операцией; API их изменения и возврата операции нет.
- L-06. Балансы и проводки меняются в одной транзакции. Кошельки блокируются через FOR UPDATE в порядке UUID.
- L-07. DEPOSIT выполняется из SYSTEM, TRANSFER — из обычного кошелька.
- L-08. Для DEPOSIT пользователь должен владеть получателем; для TRANSFER — источником. Нарушение скрывается за 404 / WALLET_NOT_FOUND.
- L-09. Бизнес-отказ откатывает денежную транзакцию: балансы, проводки и outbox не изменяются.

## Платежи

- P-01. `Idempotency-Key` обязателен для POST payments. Уникальна пара `(user_id, idempotency_key)`.
- P-02. Повтор завершённого платежа возвращает сохранённый результат. Изменение типа, суммы, валюты или кошельков даёт 409 / IDEMPOTENCY_KEY_CONFLICT. Описание не сравнивается.
- P-03. SUCCESS и REJECTED окончательны. Для FAILED и других нетерминальных состояний повтор исполняет сохранённые параметры; исходное тело и ключ нужно сохранять.
- P-04. Payment проверяет форму поручения: для TRANSFER нужен источник, для DEPOSIT источник в запросе должен отсутствовать. Проверки баланса и кошельков выполняет ledger.
- P-05. Результат вызова ledger:
  - 2xx → SUCCESS;
  - 422 / 404 → REJECTED с кодом причины;
  - 409 → публичная ошибка 409 / IDEMPOTENCY_KEY_CONFLICT;
  - остальные HTTP-ошибки и сетевые сбои → FAILED / LEDGER_UNAVAILABLE.
- P-06. REST-клиент имеет таймаут подключения 2 секунды и чтения ответа 3 секунды.
- P-07. Payment не читает таблицы ledger и не рассчитывает балансы.
- P-08. Внутренний ключ ledger и `externalRef` равны UUID платежа; повтор исполнения использует тот же UUID.
- P-09. Новый платёж возвращается с HTTP 201, существующий — с HTTP 200. SUCCESS / REJECTED / FAILED нужно смотреть в теле ответа.
- P-10. Получение чужого платежа возвращает 404.

## Выписка

- S-01. Проекция строится из событий Kafka.
- S-02. Одно событие создаёт OUT источника и IN получателя, включая SYSTEM.
- S-03. Допустимо отставание выписки от ledger. Актуальный баланс читается из ledger.
- S-04. API изменения строк выписки нет.
- S-05. Повторы проверяются по `transactionId`; дополнительно действует уникальность `(transaction_id, wallet_id)`.
- S-06. Выборка ограничена кошельком и владельцем из JWT. Чужая выписка пуста.
- S-07. Границы `from` и `to` необязательны и включительны; сортировка — по `createdAt` по убыванию. `limit` по умолчанию 50.
