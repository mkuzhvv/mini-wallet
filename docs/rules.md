# Бизнес-правила mini-wallet
Правила пронумерованы. Номер правила используется в коде и в коде ошибок,
чтобы на них можно было ссылаться

## Общие

- R-01. Одна валюта: RUB. Запрос с другой валютой — 400 VALIDATION_ERROR.
- R-02. Сумма операции: больше 0, не более 2 знаков после запятой,
  не более лимита MAX_OPERATION_AMOUNT (константа, например 1 000 000.00).
  Нарушение — 400 VALIDATION_ERROR.
- R-03. Деньги хранятся и передаются только как точные десятичные значения
  (NUMERIC(19,2) в БД, BigDecimal в Java). Никаких float/double.

## Кошельки (ledger-service)

- W-01. Кошелек создается со статусом ACTIVE и балансом 0.
- W-02. Баланс пользовательского кошелька не может стать отрицательным.
  Проверяется и в коде, и ограничением в БД (двойная защита).
- W-03. Кошелек со статусом BLOCKED не может быть ни источником, ни получателем.
  Нарушение — 422 WALLET_BLOCKED.
- W-04. SYSTEM — технический кошелек:
    - может быть только источником DEPOSIT;
    - не может участвовать в TRANSFER ни в какой роли;
    - не доступен через публичное API;
    - его баланс может уходить в минус (это выпущенные в систему деньги).
- W-05. У одного пользователя может быть несколько кошельков.

## Операции (ledger-service)

- L-01. Атомарность: операция = ровно две проводки (один DEBIT, один CREDIT)
  на одинаковую сумму. Либо проведены обе, либо ни одной.
- L-02. source_wallet != target_wallet. Нарушение — 400 VALIDATION_ERROR.
- L-03. Достаточность средств: balance(source) >= amount.
  Исключение — SYSTEM. Нарушение — 422 INSUFFICIENT_FUNDS.
- L-04. Идемпотентность: повтор команды с тем же idempotency_key возвращает
  результат существующей операции, не проводя деньги повторно.
  Тот же ключ с другим payload — 409 IDEMPOTENCY_KEY_CONFLICT.
- L-05. Проводки неизменяемы. Исправление ошибок — только новой операцией
  (reversal). В MVP reversal не реализуется, правило декларируется.
- L-06. Балансы обновляются только в одной транзакции с проводками.
  Параллельные операции на одном кошельке сериализуются блокировками строк,
  чтобы не потерять обновление.
- L-07. Типы операций: DEPOSIT (source обязан быть SYSTEM),
  TRANSFER (source обязан быть не SYSTEM).

## Платежи (payment-service)

- P-01. Заголовок Idempotency-Key обязателен для POST /api/v1/payments.
  Отсутствие — 400 VALIDATION_ERROR.
- P-02. Тот же ключ и тот же payload — вернуть сохраненный результат (200).
  Тот же ключ с другим payload — 409 IDEMPOTENCY_KEY_CONFLICT.
- P-03. Терминальными (кешируемыми как окончательные) считаются только
  SUCCESS и REJECTED. FAILED — ретраевое состояние: повтор с тем же ключом
  выполняет попытку заново.
- P-04. payment валидирует только свои поля (форма, сумма, наличие ключа).
  Денежные проверки (баланс, статусы кошельков, существование кошельков) —
  ответственность ledger. Каждый сервис валидирует только то, чем владеет.
  Поэтому payment не делает предварительных запросов кошельков:
  это лишний вызов и гонка «проверил-потом-изменилось».
- P-05. Маппинг результата команды:
    - ledger 200 POSTED -> SUCCESS;
    - ledger 422 -> REJECTED, failure_reason = код из ledger
      (INSUFFICIENT_FUNDS / WALLET_BLOCKED);
    - ledger 404 -> REJECTED, failure_reason = WALLET_NOT_FOUND;
    - ledger 409 -> ошибка конфигурации клиента, вернуть 409 как есть;
    - ledger 5xx или таймаут -> FAILED, failure_reason = LEDGER_UNAVAILABLE.
- P-06. Вызов в ledger обязан иметь таймаут (константа, например 3 секунды).
  Бесконечное ожидание запрещено: оно убивает потоки и накапливает очереди.
- P-07. payment не читает таблицы ledger и не считает деньги.
  Он только оркестрирует и хранит статусы.

## Выписка (statement-service)

- S-01. Read model строится ТОЛЬКО из событий Kafka. Прямых записей нет.
- S-02. Один TransactionPosted порождает две строки StatementEntry
  (взгляд источника и взгляд получателя). Строки для SYSTEM не создаются.
- S-03. Выписка eventually consistent: допустимо отставание от ledger.
  Критичные данные (баланс) читаются из ledger, не из statement.
- S-04. Строки выписки неизменяемы после создания.
- S-05. Консьюмер идемпотентен: повторная доставка события не создает дублей.
  Защита — unique-ограничение (wallet_id, transaction_id).

## Сквозные правила (Redis)

- X-01. Публичные endpoint'ы защищены rate limiter'ом через Redis:
  fixed window, лимит на клиента (например 60 req/min).
  Превышение — 429 RATE_LIMIT_EXCEEDED.
  Почему Redis: состояние лимитера общее для всех инстанс и имеет TTL;
  Caffeine локален, Postgres избыточен.
- X-02. Redis не является источником правды о деньгах.
  Балансы, операции и ключи идемпотентности живут в Postgres.
  Потеря данных Redis не должна приводить к потере или искажению денег.
- X-03. Кэш баланса рассмотрен и ОТКЛОНЕН.
  Чтение баланса — дешевый запрос; кэш добавил бы проблемы
  согласованности без пользы. Решение осознанное.
