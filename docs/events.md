# События Kafka mini-wallet

## Назначение

События — способ ledger-service сообщить миру «у меня произошла операция»,
не зная, кто и зачем это слушает. Сейчас потребитель один (statement-service),
позже может появиться notification-service — producer при этом не меняется.
В этом смысл слабой связанности.

## Топик

Один топик: `ledger.transaction.events`.

Имя = <сервис-владелец>.<агрегат>.events. В топике несколько типов событий,
тип указан в поле eventType. Для нашего объема этого достаточно;
если потребителей и типов станет много, разобьем на отдельные топики осознанно.

## Конверт события (общие поля)

```json
{
  "eventId": "uuid",
  "eventType": "TransactionPosted",
  "schemaVersion": 1,
  "occurredAt": "2026-08-14T10:30:00Z",
  "aggregateId": "id транзакции",
  "correlationId": "id платежа, ради которого все началось",
  "payload": { ... }
}
```

- eventId — уникален; консьюмеры могут использовать для дедупликации;
- correlationId — сквозной идентификатор цепочки для логов и трассировки;
- schemaVersion — для эволюции схемы.

## События

### TransactionPosted

Операция проведена. Из него statement-service строит выписку.

payload:

```json
{
  "transactionId": "uuid",
  "type": "TRANSFER",
  "amount": "100.00",
  "currency": "RUB",
  "sourceWalletId": "uuid",
  "targetWalletId": "uuid",
  "description": "за обед"
}
```

### TransactionRejected

Операция отклонена по бизнес-причине. Выписке не нужен
(деньги не двигались), но пригодится будущему notification-service.

payload:

```json
{
  "transactionId": "uuid",
  "type": "TRANSFER",
  "sourceWalletId": "uuid",
  "targetWalletId": "uuid",
  "reason": "INSUFFICIENT_FUNDS"
}
```

## Кто производит и кто потребляет

| Роль      | Сервис            | Что делает                                        |
|-----------|-------------------|---------------------------------------------------|
| producer  | ledger-service    | публикует Posted/Rejected через outbox            |
| consumer  | statement-service | группа `statement-service`, строит read model     |
| (позже)   | notification      | группа `notification-service`, уведомления        |

payment-service события НЕ потребляет: его статусы обновляются
синхронным ответом команды. Это осознанное решение; если перейдем
на полностью асинхронные команды — вернемся к этому вопросу.

## Надежность публикации: outbox

Нельзя просто вызвать kafka.send() внутри бизнес-транзакции:

- упадем после commit, но до send — событие потеряно;
- упадем до commit, а send уже ушел — событие про данные, которых нет.

Поэтому outbox:

1. ledger в одной транзакции пишет проводки + строку в таблицу outbox.
2. Отдельный publisher читает outbox и отправляет в Kafka, помечая отправленным.
3. Если процесс упал между 1 и 2 — событие останется в outbox и уйдет позже.

Цена: возможна повторная отправка (at-least-once). Поэтому консьюмеры
обязаны быть идемпотентными (правило S-05).

## Доставка и порядок

- Доставка at-least-once: дубли возможны, потеря — нет.
- Partition key = transactionId: события одной операции
  (если их несколько) идут в одну партицию.
- Строгий глобальный порядок не требуется: выписка сортируется
  по occurred_at при чтении, а не по порядку доставки.

## Ошибки консьюмера

- Бизнес-ошибка (например, дубль по unique) — не ретраить бесконечно,
  событие считается обработанным.
- Техническая ошибка — ретраи с ограниченным числом попыток,
  затем сообщение уходит в dead letter topic (DLQ) для разбора.
  Конкретные числа (попытки, бэкфофф) выберем при реализации.

## Эволюция схемы

- Поля только добавляются, никогда не удаляются и не переименовываются.
- Консьюмеры игнорируют неизвестные поля.
- Несовместимое изменение — новый eventType или новый топик.
